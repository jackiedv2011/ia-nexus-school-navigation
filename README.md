# IA Nexus — school navigation & chatbot

A navigation assistant for Independence Academy. Students can ask where a
teacher is, get turn-by-turn directions between any two rooms, see a drawn
route on the floor plans, keep their own class schedule, and be routed to their
next class automatically when the bell is about to ring.

- **Chat** (`/`) — rule-based assistant, open to guests; an Anthropic-backed
  "Interactive" mode for signed-in users.
- **Route Finder** (`/route`) — pick any two rooms, get the shortest walk drawn
  on the floor plan. Open to everyone, no account needed.
- **My Schedule** (`/schedule`) — per-account, cloud-synced class schedule with
  a live bell-schedule countdown and an automatic route to the next class.
- **Teacher Directory** (`/teachers`) — every teacher's room, period by period.
- **Admin** (`/admin`) — read-only moderation and usage dashboard, gated by
  `ADMIN_KEY` (not a user account). Disabled entirely when that is unset.

## Prerequisites

- **Node.js 22** (CI pins 22; `render.yaml` pins 22.12.0)
- **A Postgres database.** The backend refuses to boot without one. The project
  is set up for Supabase — use the **Transaction pooler** connection string
  (port 6543), not the direct one, which is IPv6-only.

## Install

```bash
npm run install:all      # installs backend/ and frontend/
cp backend/.env.example backend/.env
```

Then fill in `backend/.env`. Every variable is documented in
`backend/.env.example`; the only two that are strictly required are:

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | always | Postgres connection string. No fallback — the server exits without it. |
| `JWT_SECRET` | in production | Signs session tokens. Dev falls back to a clearly-labelled insecure default. |
| `ANTHROPIC_API_KEY` | for Interactive mode | Without it, rule-based chat still works; Interactive mode returns an error. |
| `EMAIL_*` | for real emails | Without them, password-reset codes and verification links print to the server console instead. |

## Run

```bash
npm run dev              # backend on :3001 + frontend on :5183, together
```

The frontend dev server proxies `/api` to `http://localhost:3001`, so open
**http://localhost:5183**. The port is deliberately 5183, not Vite's default —
see the comment in `frontend/vite.config.js`.

## Build

```bash
npm run build --prefix frontend    # emits frontend/dist
```

In production the backend serves `frontend/dist` itself, on the same origin, so
there is no CORS configuration and no separate frontend host.

## Test

```bash
npm test --prefix backend      # 60 tests (+ 9 more that need a database)
npm test --prefix frontend     # 104 unit tests
npm run test:e2e --prefix frontend   # 31 end-to-end tests, in a real browser
```

**Backend** — `route`, `routes`, `chatbot`, `audit`, `route-api` and
`data-consistency` are pure and run anywhere. `admin-api` boots the real server
with the database stubbed, so it exercises the actual authorization chain
without needing Postgres. `security.test.js` needs a real database: it runs the
server against a throwaway Postgres schema and **skips itself** with a printed
reason when `DATABASE_URL` is unset — set it to run those nine checks too.

**Frontend** — Vitest + jsdom (`npm run test:watch --prefix frontend` to watch).
Covers the bell schedule, the storage helper, the walking-time estimate,
saved-route parsing, the markdown/HTML escaping in chat messages, the modal
focus trap, and a lint that no CSS module declares the same class twice (which
silently broke the admin header once).

**End-to-end** — Playwright drives a real Chromium against the real app: the
actual backend with only its database stubbed (`frontend/e2e/fake-backend.cjs`)
behind the real Vite dev server and its `/api` proxy. Both servers are started
by the Playwright config, so `npm run test:e2e` is the whole command. Covers the
Route Finder (happy path, both floors, validation, a 404 from the API, the
backend being unreachable, keyboard use), guest chat and its inline route map,
the admin dashboard's key gate, and routing/responsiveness across the public
pages. The fixture **fails any test that makes an off-origin request**, which is
what keeps a third-party asset from creeping back onto the critical path.

If your environment already has a Chromium that Playwright's bundled version
doesn't match, point at it: `PW_CHROMIUM=/path/to/chrome npm run test:e2e`.

All three suites run in CI on every push and pull request.

## Deploy

`render.yaml` describes the Render service: it builds the frontend (with
`--include=dev`, because vite is a devDependency), installs the backend, and
runs `node backend/server.js`. `JWT_SECRET` and `ADMIN_KEY` are generated by
Render; `DATABASE_URL`, `ANTHROPIC_API_KEY` and the email credentials must be
set by hand in the dashboard.

## Where the map data lives

All building data is in **`backend/data/roomCoordinates.js`**, and it is the
single source of truth. Nothing else in the repo should describe the building.

Every coordinate is in the **original blueprint's 2448×1584 pixel space**. The
floor plan images the school issued are a redrawn version at a different scale
and crop, so `frontend/src/components/NavigationMap.jsx` carries a per-floor
`{ scale, dx, dy }` transform that maps blueprint space onto each image:

```
imageX = blueprintX * scale + dx
imageY = blueprintY * scale + dy
```

That means **replacing the floor plan drawings does not require touching a
single coordinate** — re-run the image registration and update those six
numbers.

The four structures you edit to change the building:

| Structure | What it is |
|---|---|
| `CORRIDORS[floor]` | The walkable hallways, as axis-aligned segments (`{y, xMin, xMax}` / `{x, yMin, yMax}`). These are the ONLY routes through the building. |
| `ROOM_DOORS['floor:roomkey']` | Every doorway of a room, as `[x, y]`. A room may have several; the router picks the pair that makes the walk shortest. Two rooms sharing a wall may list the same point — that is one shared door. |
| `ROOM_LABELS[floor]` | Exactly the rooms the school lists, in the form shown to a student. Drives the Route Finder's pickers. |
| `STAIR_POSITIONS[stair][floor]` | Each stairwell's landing on each floor. **A stairwell with no entry for a floor has no landing there**, and the router will never route through it on that floor. |

### How a route is computed

1. `buildFloorGraph(floor)` turns the corridors into a graph: every corridor
   intersection becomes a node, and every doorway and stair landing is
   projected **perpendicularly** onto the nearest corridor and joined to it by
   a short right-angle stub. Junctions within `JUNCTION_TOL` (30px) of touching
   are snapped together, because the hand-drawn plans they came from wobble.
2. The three graphs are built once at module load and cached.
3. `findPath` runs **Dijkstra** (`dijkstra()`) over the relevant floor graph.
   A room with several doorways gets a temporary one-way "terminal" node joined
   to each door at zero cost, so one Dijkstra run returns the cheapest doorway
   on each end. The terminals are one-way specifically so nobody's route can
   walk in one door of a room and out the other for free.
4. Across floors, it runs Dijkstra once per **usable** stairwell (one with a
   landing on both floors) and keeps the cheapest total. That is why
   `STAIR_POSITIONS` omitting a floor is the whole mechanism for "this
   stairwell doesn't reach that floor".

Edge weights are straight-line pixel distance between adjacent nodes — one
consistent unit throughout. There are no negative or zero weights outside the
deliberate room terminals, and `backend/test/audit.test.js` asserts that.

### Adding or moving a room

1. Add its label to `ROOM_LABELS[floor]` **and** to `ROOMS` in
   `frontend/src/pages/RoutePage.jsx` (the picker's copy — the frontend cannot
   import from the backend, so the lists are duplicated; a test enforces that
   they stay identical).
2. Add its doorway(s) to `ROOM_DOORS` under `'<floor>:<lowercased, spaces removed>'`.
3. Run `npm test --prefix backend`. `routes.test.js` walks every one of the
   ~6,000 ordered room pairs and checks each route starts at a doorway, ends at
   a doorway, turns only at right angles, and never leaves a hallway — so a bad
   coordinate shows up immediately. `data-consistency.test.js` will also fail if
   you forget step 1's second half: it parses `RoutePage.jsx` and compares the
   two room lists.
4. `route.test.js` holds point-count snapshots for a handful of routes. If your
   change legitimately alters one, update the snapshot in the same commit.

### The chatbot's building knowledge

**There isn't any, and that is deliberate.** Both chat engines used to carry
their own prose description of the building, and both had drifted out of step
with the plans — naming a Floor 1 landing for Stair 2 that does not exist, and
disagreeing with the actual shortest route on more than half of all cross-floor
trips.

Now:

- `chatbot-rules.js` answers a directions question by calling `findPath` and
  reporting what it returned (floors, stairwell, distance, walking time). It
  writes no turns of its own. `ROOM_CLUSTERS` survives only to name which wing
  a room is in.
- `chatbot-llm.js` is instructed not to invent turn-by-turn directions at all,
  and its stairwell-availability list is generated from `STAIR_POSITIONS`
  rather than written by hand.
- The frontend draws the real route map under any assistant message that
  describes one (`InlineRouteMap`). The map is the directions.

One thing to know before editing `ROOM_CLUSTERS`: `getRoomCluster` returns the
**first** range containing a room, so an overlapping wing must be listed
**before** the wider one that contains it.

## Admin dashboard

`/admin` is gated by `ADMIN_KEY` — a single shared secret sent as an
`x-admin-key` header, deliberately **not** tied to the user/role system (this
app has no concept of an admin account). Leave `ADMIN_KEY` unset and the
dashboard rejects every request.

It shows usage counts and a 7-day trend, the question feed with what the bot
answered and whether it managed to, profanity-flagged messages, star-rating
feedback, security events (failed logins, rate-limit trips, honeypot hits), and
its own access log. Every access attempt, successful or not, is recorded in
`admin_audit_log`.

Every endpoint is **read-only**: a leaked key exposes information but cannot
change or delete anything. Content is purged on the retention schedule the
dashboard itself displays (`ANALYTICS_RETENTION_DAYS` and friends in
`server.js`).

## Third-party dependencies at runtime

The browser loads nothing from a third party. The webfonts are self-hosted under
`frontend/public/fonts/`, so the CSP is `'self'` for scripts, styles, fonts and
connections. The end-to-end suite enforces it: any off-origin request fails the
test that made it.

To refresh the fonts, see the header comment in `frontend/public/fonts/fonts.css`.
